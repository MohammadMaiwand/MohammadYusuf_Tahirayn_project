# Authentication and account management — Master Prompt 03

Current implementation date: 2026-11-13, Asia/Kabul. This record supersedes older no-login, no-account and external-identity-only descriptions. Operational Sham Shaban remains disabled.

## Login and account lifecycle

Login fields are role, branch (hidden for admin), employee name, email, password and CAPTCHA. The backend compares actual stored role/name/branch and verifies the Argon2id hash; selecting a role never grants it. Email is trimmed and lowercased, names use NFKC and collapsed whitespace. Failures return a generic error rather than revealing which account field matched. CAPTCHA supports a short-lived image or readable arithmetic challenge; both are server-validated, signed and single-use. Refreshing the challenge does not bypass rate limits.

There is no public registration. Admin can create and edit managers/employees across active branches; manager can manage only employees in their one assigned branch. Self grant changes are denied. Status supports active, suspended and deactivated; disabled accounts cannot log in or refresh. Account changes use optimistic grantVersion and revoke sessions. Password change requires the current password; authorized resets set a new hash and revoke sessions. Passwords require 8?128 characters; composition constraints were superseded by the owner on 2026-11-19. Password reset is an administrative workflow; no unconfigured email-delivery or public recovery claim is made.

## Sessions and authorization

Opaque random cookies contain no role or branch claims. MongoDB stores only SHA-256 secret digests. Access expires in 15 minutes; absolute session/refresh expiry is seven days. Refresh rotates both secrets atomically and retains digest history to revoke the session on detected reuse. Logout and explicit revocation invalidate server sessions. Cookie flags are HttpOnly, SameSite Strict, API path, and Secure in production. Allowed Origin validation plus a custom request header protect cookie mutations. Production must use HTTPS and explicitly configured same-site frontend/API origins.

Every authenticated request reloads account state and effective database grants. Every branch route validates active branch membership; services filter records by branchId and scope transaction ownership. Admin scope is all four active branches; manager/employee scope is exactly one. Shared permission defaults plus allow/deny overrides define effective authority; deny wins. Managers can delegate only the employee allowlist within their own effective permissions, including defaults and catalog implication expansion. Global session access requires admin role and sessions.manage; other callers see/revoke only their sessions. Only admin with security.read can read global security audit events.

## Interface and business integration

Admin has consolidated real database metrics, branch comparison and branch selection. Manager has assigned-branch metrics, delivery counts, recent registrations, transactions and permitted activity. Employee has simple operational links and permitted recent transactions. Account permissions use grouped translated checkboxes, category collapse, select/deselect all, confirmation and cancel. Accounts show status, role, branch, creation and last login. Sessions and password screens provide self-service and authorized global controls.

MongoDB notifications retain per-user read state and branch/customer context; polling refreshes lists and counters. Branch messages persist independently of login. Employee transaction notifications respect ownership; branch messages are visible within the authorized branch. Admin can switch notification scope across active branches. Existing A5 and paired A4 invoice rendering remains in use. WhatsApp links use only authorized invoice snapshots, normalize the customer's number and open a reviewable message with invoice/customer/branch/amount details. The application does not automatically send or claim delivery. Print / Save PDF opens the browser workflow; PDF attachment sharing depends on saving and attaching the file in the destination app.

Dari, Pashto and English resources cover authentication/account/permission/security screens with immediate RTL/LTR switching. Automated mobile containment complements, but does not replace, native speaker and physical-device acceptance.

## Offline policy

An online authenticated session may receive an Ed25519 signed lease, bound to the device and complete authorization profile, for up to eight hours (bounded by absolute server session expiry). The browser verifies using VITE_AUTH_PUBLIC_KEY. Missing/mismatched public key fails closed for real offline authentication. No password or cookie secret is stored in IndexedDB/localStorage. AES-GCM cache scope includes subject, branch, device and permission digest. No new accounts, grants or passwords can be issued offline. Replay rechecks current grants, device and record branch.

The app checks identity every 15 seconds and on reconnect independently of business sync flags. Offline expiry blocks further operations and returns the user to login. A disconnected device cannot instantly learn of remote deactivation; its existing lease may last until expiry. Logout removes the lease and clears memory queries while retaining scoped encrypted cache/outbox for recovery. Browser storage encryption does not protect against same-origin compromise, a controlled browser profile or an unlocked device. Device clock manipulation is outside this application's trust boundary. Retention and managed-device policies remain operational work.
